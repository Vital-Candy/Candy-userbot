# Candy Userbot 2.0

Модульный Telegram userbot на Python + Telethon. Требуется Python ≥ 3.11.

## Быстрая установка (Termux и Linux)

Скопируйте и выполните в терминале, установщик сам поставит Python, git и зависимости:

```text
bash <(curl -fsSL https://raw.githubusercontent.com/Vital-Candy/Candy-userbot/main/installer.sh)
```

Проект ляжет в `~/userbot`. Первый запуск (бот спросит API ID и API Hash с https://my.telegram.org/apps, телефон и код из Telegram):

```text
cd ~/userbot && ./run.sh
```

Если команда с `curl` не сработала, то же самое вручную:

```text
pkg update -y && pkg install -y git curl
git clone https://github.com/Vital-Candy/Candy-userbot.git ~/userbot
bash ~/userbot/installer.sh
```

(на Debian и Ubuntu вместо `pkg` используйте `sudo apt install -y git curl`). Другая папка: `CANDY_DIR=~/my-bot bash installer.sh`.
В Termux держите проект в домашней папке (`~`), а не в `/sdcard`: там нельзя выдать права на запуск.
Обновление потом делается командой `.update` в Telegram или пунктом «Обновление» в меню.
Не отправляйте никому папку `data/`, коды из Telegram, API Hash и пароль 2FA.

## Команды в Telegram

`.help` показывает короткий список команд и что они делают. `.help <команда>` (точку писать не нужно) показывает полное описание: как пользоваться, все подкоманды и аргументы, кому доступна команда. Например, `.help label` или `.help account`. Справка есть и у команд ваших плагинов: она берётся из параметров `description`, `usage` и `details` при регистрации команды.

`.status` показывает одну короткую сводку состояния, а `.status all` добавляет список модулей и фоновых задач с причинами сбоев. Отдельной команды `.health` больше нет. В сводке есть и занятая память процесса. Если фоновая задача начала падать (три сбоя подряд), userbot сам пришлёт предупреждение в «Избранное».

`.restart` (владелец и ADMIN) корректно перезапускает userbot: например, после правки `.env`. Модули останавливаются как обычно (часы возвращают имя), процесс стартует заново.

## Повтор сообщения (`.spam`)

```
.spam "<текст>" [повторов] [-d пауза]
.spam stop
```

Примеры: `.spam "привет"` (один раз), `.spam "привет" 5` (пять раз с паузой 1 секунда), `.spam "скажи "привет"" 3 -d 0.5` (три раза с паузой 0.5 с).

- Текст берётся между первой и последней кавычкой, кавычки внутри текста не мешают. Подходят и «умные» кавычки клавиатуры.
- Сообщение уходит как есть, без Markdown. Сама команда после запуска удаляется.
- Защита: от 1 до 200 повторов, пауза от 0.1 с, текст до 4096 символов, в одном чате идёт одна отправка. `.spam stop` останавливает всё, остановка userbot тоже.
- Если Telegram просит подождать (FloodWait), пауза делается сама. При долгом ожидании или ошибке (например, нет прав писать в чат) отправка прекращается, а в «Избранное» приходит уведомление.

## Утилиты: `.user`, `.ping`, `.tag`, `.purge`, `.mute`

- `.user <id или @username> [--not-private]`: сведения об аккаунте (ID, имена, username, био, статус, язык, общие чаты, день рождения, признаки Premium, бот, проверенный и т. д.). Все значения моноширинным шрифтом: нажатие копирует. Флаг `--not-private` добавляет номер телефона, если Telegram его вам показывает. Без аргумента работает ответом на сообщение. Для контактов Telegram отдаёт имя так, как оно записано у вас в контактах: имя из профиля через API получить нельзя.
- `.ping`: пинг до Telegram (служебный запрос ping, середина из трёх замеров) и сообщение меняется на pong.
- `.tag all [-e @юзер ...]` и `.tag rand <число> [-e @юзер ...]`: отметить участников группы (у кого нет username, имя со ссылкой на аккаунт). Исключения в `-e`: `@username`, `username` или ID. Боты, удалённые аккаунты и вы сами пропускаются. Все отметки идут одним сообщением (делятся на части только при превышении предела Telegram), не больше 300 за раз; `.tag stop` останавливает.
- `.purge <N> [all]`: тихо удаляет последние N ваших сообщений в этом чате (от 1 до 1000). Команда удаляет себя первой, ответа в чате нет. Удаляется ровно N или меньше: сама команда не считается, больше N не удаляется никогда. С `all` удаляются последние N сообщений всех участников, для этого нужны права администратора на удаление (в личном чате удаляются сообщения обеих сторон). Без прав ничего не удаляется, а в «Избранное» приходит объяснение. Ошибки тоже приходят только в «Избранное».
- `.mute [длительность] [--all] [-user|-trusted|-admin]`: тихо удаляет новые сообщения, пока режим включён. Длительность: `30s`, `10m`, `2h`, `1d`, `1h30m` (число без буквы: минуты), без неё режим бессрочный. В личном чате удаляется всё новое (и ваше, и собеседника), в группе только ваши сообщения. В группе `--all` удаляет сообщения всех, кроме ваших (флаг уровня `-user`, `-trusted` или `-admin` оставляет право писать тем, у кого выдан этот уровень или выше, а без флага писать можете только вы; флаг работает и в личном чате, но не вместе с ответом на сообщение): проверяются права на удаление, затем нужно дважды подтвердить ответом на сообщение с командой (сначала `да`, потом `подтверждаю`). Команда ответом на сообщение пользователя в группе удаляет все его новые сообщения (нужны права на удаление). Остановка: ответить на сообщение с командой словом `stop` (или `стоп`): оба сообщения удалятся. Запасные способы: `.mute off` в этом чате и `.mute list` (все режимы). Режимы сохраняются в базе и возобновляются после перезапуска userbot; по окончании или при ошибке прав в «Избранное» приходит сводка. Сообщения удаляются пачками до 100 штук; пока режимов нет, наблюдатель за сообщениями не подключён и ничего не расходует.

## Префикс команд (`.setprefix`)

`.setprefix` показывает текущий префикс, `.setprefix !` задаёт новый (1–3 символа, без пробелов, букв, цифр и `@`), `.setprefix reset` возвращает точку. Префикс хранится отдельно для каждого аккаунта и сохраняется после перезапуска. В `.help` имена команд показываются с новым префиксом, но подсказки внутри других ответов могут оставаться с точкой.

## Часы в имени (`.time`)

Модуль `modules/clock` показывает время в имени аккаунта: после имени через пробел, например `Candy 12:34`. Имя меняется ровно в начале каждой минуты (запрос уходит чуть раньше границы, поправка на задержку сети считается сама).

```text
.time            меню: 22 стиля с живыми примерами; выберите стиль, ответив на это сообщение номером
.time on 5       включить часы в стиле 5 (если уже включены, просто сменит стиль)
.time on         включить с прежним стилем (если стиль не выбирали, покажет меню)
.time off        выключить часы и вернуть имя
.time tz +5      часовой пояс: смещение (+5, -3:30), имя (Asia/Samarkand) или auto
```

Если часы уже включены, меню предлагает сменить стиль или выключить (ответ `0`). Меню принимает ответ 5 минут и только на своё сообщение, поэтому обычные числа в чатах ничего не меняют.

Как это защищает имя:
- исходное имя сохраняется в базе до первого изменения; при `.time off`, `.stop` и любой остановке userbot оно возвращается. Если процесс убит принудительно, имя вернётся при следующем запуске;
- имя никогда не обрезается: если имя вместе с часами длиннее 64 символов, часы не включаются, а в ответе сказано, до скольки символов сократить имя;
- если вы сами сменили имя, часы подстроятся под новое, ничего не затирая;
- если у аккаунта есть фамилия, часы ставятся после неё, а имя не трогается;
- после остановки userbot часы убираются, а при следующем запуске включаются сами (`.time off` отключает насовсем).

Время берётся с часов устройства. Если в Termux оно идёт по UTC, задайте пояс: `.time tz +5`. При слишком частых изменениях Telegram может попросить подождать (FloodWait): модуль подождёт и продолжит. Задача `clock.tick` видна в `.status all`.

## Архитектура

Подробности, принятые решения и план этапов: [ARCHITECTURE.md](ARCHITECTURE.md).

- `core/` — lifecycle, dispatcher, events, modules, plugins, console.
- `accounts/` — мультиаккаунты, авторизация и backup.

## Запуск и остановка

```text
python main.py
```

Остановка: Ctrl+C, `kill -TERM <pid>`, `kill -HUP <pid>`, команда `.stop` в Telegram или `stop` в консоли.
Все они запускают одну и ту же штатную остановку. Второй сигнал во время остановки завершает процесс сразу.
Под `nohup` сигнал SIGHUP игнорируется, как и положено.

Коды выхода:

| Код | Когда |
|---|---|
| 0 | штатная остановка |
| 1 | сбой запуска, фатальная ошибка, потеря связи с Telegram: стоит перезапустить |
| 2 | ошибка настройки или входа (невалидная сессия, закрытый stdin при первом запуске, повреждённая база): нужен человек, перезапуск не поможет |
| 130 | принудительный выход по второму сигналу |

Супервизор перезапускает процесс только после кода 1. Код 2 нарочно исключён, иначе отозванная сессия гоняла бы перезапуски по кругу.

### Постоянная работа (Termux и Linux)

```text
./run.sh                       # перезапуск после сбоев с нарастающей паузой
python main.py --check         # проверка окружения без подключения к Telegram
```

`run.sh` останавливается на кодах 0, 2 и 130, пересылает SIGTERM/SIGINT дочернему процессу и в Termux держит `termux-wake-lock`, если установлен termux-api. Настройки: `CANDY_RESTART_MIN`, `CANDY_RESTART_MAX` (паузы, с), `CANDY_STABLE_AFTER` (после скольких секунд работы сбой не считается быстрым), `CANDY_MAX_FAST_FAILS` (0 — без ограничения).

Для systemd есть образец юнита `deploy/candy-userbot.service` (`Restart=on-failure`, `RestartPreventExitStatus=2`). Вход в аккаунт делается заранее: `python main.py --add-account`.

`--check` ничего не меняет (база открывается только на чтение) и проверяет Python, Telethon, права на каталоги, версию схемы базы, активный аккаунт и файл сессии.

### Терминальное меню

В терминале (Termux, Linux) после запуска экран очищается и показывает логотип, активный аккаунт, состояние, версию и меню:

```text
1  Аккаунты                    список, переключение, добавление, резервная копия
2  Логи в реальном времени     последние строки и новые события; Enter: назад
3  Обновление                  проверка GitHub и установка новой версии
4  Остановить бота             с подтверждением
```

Выбор: номер и Enter; пустой Enter обновляет экран. Пока меню открыто, логи в консоль не выводятся (они идут в `logs/candy.log` и в пункт 2), чтобы не портить экран. Свой логотип: положите ASCII-рисунок в `logo.txt` в корне проекта (до 20 строк, длинные строки обрезаются по ширине экрана); без файла показывается встроенный. Обновление `logo.txt` не перезаписывает. Старая строка команд `candy>` включается так: `CANDY_UI=console`. Без терминала (nohup, systemd) меню не запускается.

### Обновление из GitHub (`.update`)

Команда `.update` (только владелец и ADMIN) или пункт 3 в меню:

```text
.update          проверить и, если версия новее, установить и перезапуститься
.update check    только проверить
```

Как это работает:
- Версия берётся из `core/version.py` (`CORE_VERSION`) в ветке `main` репозитория `Vital-Candy/Candy-userbot`. Чтобы выпустить обновление, поднимите `CORE_VERSION` и запушьте в `main`: без смены версии пользователи обновление не увидят.
- Понижать версию нельзя: если на сервере версия ниже или такая же, ничего не ставится. Сравнение числовое (`1.10` новее `1.9`).
- Нужен только интернет: git не требуется. Архив ветки скачивается по HTTPS только с доменов GitHub.
- Архив проверяется до замены файлов: безопасность путей, отсутствие ссылок, размер, версия внутри архива, синтаксис всех `.py`.
- `data/`, `logs/`, `plugins/`, `.env` и `logo.txt` не затрагиваются. Файлы, удалённые из новой версии, убираются из пакетов (`core/`, `modules/` и т.д.).
- Прежние файлы сохраняются в `data/update/backup-<версия>/`; если замена оборвалась, всё возвращается автоматически.
- Если изменился `requirements.txt`, бот предупредит: выполните `pip install -r requirements.txt` и перезапустите.
- После установки бот перезапускается сам (под `run.sh` тоже).

Важно: обновление исполняет код из репозитория. Включите двухфакторную защиту на GitHub-аккаунте, который может пушить в `main`. Если новая версия не стартует, верните файлы вручную из `data/update/backup-<версия>/` (скопируйте поверх проекта).

Свой форк: `CANDY_UPDATE_REPO=владелец/имя`, `CANDY_UPDATE_BRANCH=ветка`.

### Логи

Логи идут в консоль и в `logs/candy.log` (ротация, права `600`). Если каталог недоступен, userbot только предупреждает и работает дальше.

## События и команды

Модули не работают с обработчиками Telethon напрямую, только с диспетчером (`app.dispatcher`).

```python
from core import filters as F
from core.reply import answer

dispatcher.register("new_message", handler, priority=10, filters=(F.private, F.incoming))
dispatcher.register_command("ping", ping, filters=(F.private,))   # в группе молча не сработает

async def ping(event):
    args = dispatcher.get_command(event).args
    await answer(event, "pong")
```

- Фильтры: `incoming`, `outgoing`, `private`, `group`, `channel`, `is_reply`; комбинаторы `all_filters`, `any_filter`, `not_filter`. Работают и обычные, и асинхронные фильтры.
- `answer(event, text)`: единый ответ. «Сообщение не изменилось» считается успехом, короткий FloodWait (до 10 с) ждёт и повторяет, остальные ошибки редактирования заменяются новым сообщением. Не бросает исключений.
- Обработчики одного события идут по очереди (приоритет, затем порядок регистрации). Каждый ограничен по времени: зависший прерывается, остальные продолжают. Упавшая или зависшая команда сообщает об этом в чат.
- `events.Raw` подключается к Telegram только пока есть raw-обработчики.

## Модули и фоновые задачи

```python
class MyModule(Module):
    name = "my.module"
    required = False          # True: сбой запуска останавливает userbot
    requires = ("system.status",)   # эти модули запускаются раньше
```

- **Сбой при запуске.** Необязательный модуль (по умолчанию) только помечается FAILED, а владелец получает сообщение в «Избранное». Обязательный модуль останавливает запуск с откатом (код выхода 1). Все системные модули (`system.*`) обязательные, `storage.labels` необязательный.
- **Зависимости.** `requires` задаёт порядок запуска, остановка идёт в обратном порядке. Если зависимость не запустилась, зависимый модуль пропускается. Неизвестная зависимость и цикл считаются сбоем запуска.
- **Фоновые задачи** имеют состояние `RUNNING` / `FAILING` / `STOPPED`, счётчики запусков и сбоев, время и текст последней ошибки. После 3 сбоев подряд пауза между попытками удваивается (не больше 5 минут), в лог идёт один traceback и редкие короткие предупреждения. Первый же успех сбрасывает серию.
- `.status all` в Telegram и `status all` в консоли показывают всё это, включая ошибку последнего сбоя.

## База данных, метки и права

SQLite (`data/database/candy.sqlite3`, WAL). Схема лежит в `storage/migrations/NNN_имя.sql`, номера идут подряд с 1.

- **Версия базы** проверяется первой, до любых изменений. База от более новой версии отвергается с понятной ошибкой (код выхода 1), файл при этом не трогается.
- **Миграции:** каждая в своей транзакции, при ошибке откатывается целиком, база остаётся на прежней версии. Перед обновлением существующей базы рядом создаётся копия `candy.sqlite3.v<версия>.bak`.
- **Транзакции:** `with db.transaction():` (вложенные блоки используют SAVEPOINT). Вне блока каждая операция сразу фиксируется.

Метки (все данные изолированы по аккаунту):

```text
.label <имя>     ответом на сообщение: поставить метку
.labels          ответом: показать метки сообщения
.goto <имя>      ссылка на сообщение с меткой (до 10 последних)
.unlabel <имя>   ответом: снять метку
```

В имени нельзя использовать символы Markdown (`* ~ ` | [ ] ( ) \` и `__`): в Telethon нет экранирования, поэтому такое имя сломало бы сообщение. Старые метки с такими символами при выводе обезвреживаются.
Ссылки: каналы и супергруппы дают `https://t.me/c/…`, личные чаты и «Избранное» дают `tg://openmessage…`, у обычных групп ссылки не бывает.

Права доступа: четыре уровня `user` < `trusted` < `admin` < `owner`. `owner` это сам аккаунт, он есть всегда, без записи в базе, и ничто из ниже описанного на него не влияет. Остальным уровень нужно выдать: у кого он не выдан, того команды молча игнорируются (ни ответа, ни ошибки).

```text
.perm list [id]
.perm grant <id | ответом> <user|trusted|admin>
.perm revoke <id | ответом> [user|trusted|admin]
.perm audit [N]                   сводка прав, замечания и последние N изменений (до 50)
.perm cmd                         пронумерованная таблица: у какой команды какой уровень
.perm cmd <команда> <user|trusted|admin|owner|default>
.perm cmd tag ping user           сразу несколько команд (пробел или запятая), уровень последний
.perm cmd 2 5 trusted             команды можно указывать номерами из таблицы
.perm cmd all trusted             все открытые команды (кроме .perm)
.perm cmd <команда> off           то же, что owner: закрыть для всех, кроме владельца
.perm cooldown                    паузы по уровням и вес пауз у команд
.perm cooldown trusted 4          базовая пауза уровня в секундах (от 0.5 до 3600), меняет владелец
.perm cooldown reset              паузы по умолчанию
.perm cmd reset                   вернуть все уровни по умолчанию
```

Что могут уровни по умолчанию (только команды, зарегистрированные с `level`; все остальные доступны одному владельцу и открыть их нельзя):

| Команда | Уровень | Для чужих |
| --- | --- | --- |
| `.help` | user | только команды, доступные его уровню |
| `.ping` | user | пинг до Telegram |
| `.user` | user | ID, username, ссылка, признаки; без имени, био, телефона |
| `.user` | trusted, admin | то же и био, статус, язык и т. п.; без телефона, без общих чатов, без признаков вашей адресной книги и без имени из ваших контактов |
| `.status` | trusted | короткая сводка (без памяти, модулей, задач, ошибок) |
| `.tag` | trusted | только `.tag rand` до 10 человек без `-e`, одним сообщением |
| `.perm` | admin | выдаёт и снимает `user` и `trusted`, смотрит таблицу команд |

Ограничения admin, которые не снимаются: он не выдаёт и не снимает `admin`, не меняет свои уровни и уровни другого admin, не меняет `.perm cmd` (это может только владелец), не может переключать аккаунты, обновлять, перезапускать, делать бэкап, управлять плагинами и префиксом: эти команды вообще не имеют уровня. Номер телефона видит только владелец (`.user --not-private`), а у других этот флаг не действует. Чужие вызовы идут через общий барьер: проверка уровня, пауза между командами одного человека, любая ошибка проверки означает отказ.

Паузы (перезарядка) есть у всех, кроме владельца, и зависят от уровня: чем ниже уровень, тем длиннее. По умолчанию user 5 с, trusted 3 с, admin 1 с, но нулевой не бывает ни у кого, даже у admin (минимум 0.5 с). После команды человек ждёт паузу своего уровня, умноженную на вес команды: `.ping` и `.user` x2, `.status` x3, `.tag` x20 (то есть trusted ждёт 60 с, admin 20 с). Владелец меняет паузы командой `.perm cooldown`; правило `user ≥ trusted ≥ admin` не даст сделать admin медленнее user. Настройки лежат в базе, `.update` их не сбрасывает. Если человек с правом на команду написал слишком рано, он получает один ответ «Подождите N с», остальные сообщения в это окно молча игнорируются; у тех, кому уровень не выдан, ответа нет вообще.

`.perm audit` показывает, сколько людей на каком уровне, какие команды открыты шире обычного, у кого выдано несколько уровней, кто выдал уровень, а сам уже не имеет прав, и журнал последних изменений (кто, когда, что). Журнал хранится в той же базе и не растёт больше 100 записей. Если хоть одно имя или номер в `.perm cmd` неверны, не меняется ничего. `.perm` нельзя опустить ниже `admin`.

`.perm cmd` меняет уровень любой команды, у которой он есть (например открыть `.tag` для `user` или закрыть `.ping` для всех, кроме владельца: `owner`). Настройки лежат в базе (`data/`), которую `.update` не трогает, поэтому после обновления они сохраняются. Если у команды после обновления поменялся уровень по умолчанию, ручная настройка всё равно остаётся в силе, пока вы не сделаете `default`.

Модуль может открыть команду и по-старому: `allow_incoming=True` с обязательными фильтрами:

```python
from core.access import require
dispatcher.register_command("ping", ping, allow_incoming=True,
                            filters=(require(app, "trusted"),))
```

Новая команда делится с другими так: `register_command("имя", обработчик, level="trusted")`; внутри `dispatcher.caller_level(event)` вернёт уровень вызвавшего (у владельца `owner`), по нему обработчик решает, что показывать.

`require(app, level)` при любой ошибке проверки отказывает. Ответ на чужое сообщение отправляется как reply, а не правкой.

## Аккаунты и backup

Одновременно работает один аккаунт. Остальные хранятся в `data/accounts/<id>/`.

Командой строки:

```text
python main.py --add-account        # добавить аккаунт или войти заново и выйти
python main.py --restore ZIP        # восстановить аккаунт из backup и выйти
```

`--add-account` для уже существующего аккаунта предлагает заменить сессию: так лечится отозванная сессия.
Вход повторяет неверный код и пароль 2FA (до 3 попыток), понятно сообщает о неверных API ID/Hash, номере и FloodWait.

В Telegram (и в консоли без точки):

```text
.account                         # список, активный отмечен ●
.account use <id|@имя>           # переключиться: штатная остановка и перезапуск процесса
.backup create [id|@имя]         # backup в data/backups/<id>-<дата>.zip
.backup list
.backup restore <файл.zip>       # имя из data/backups или путь; существующий аккаунт не перезаписывается
```

Переключение останавливает userbot штатно и запускает процесс заново (`os.execv`). Под супервизором код выхода остаётся 0.

Backup содержит `profile.json` и `session.session`: это полный доступ к аккаунту, храните его в секрете. Сессия копируется через SQLite backup API, поэтому снимок согласован, даже если бот работает.
Restore проверяет архив: пути (traversal), дубликаты, набор файлов, размеры.

Формат профиля версионируется (`accounts/migration.py`). Старый профиль мигрирует при загрузке, исходник сохраняется как `profile.json.bak`. Профиль от более новой версии отклоняется.

Права: каталог аккаунта `700`, файлы `600`. На общем хранилище Android (`/storage/emulated/0`) chmod не действует, держите `data/` во внутреннем каталоге Termux (`~/`).

### Необязательный `.env`

Файл `.env` в корне проекта читается, если он есть (образец: `.env.example`). Переменные окружения приоритетнее файла.

| Переменная | По умолчанию | Значение |
|---|---|---|
| `CANDY_DATA_DIR` | `data` | каталог аккаунтов, базы и бэкапов |
| `CANDY_LOG_LEVEL` | `INFO` | `DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL` |
| `CANDY_HANDLER_TIMEOUT` | `30` | секунд на обработчик события; `0` — без лимита |
| `CANDY_COMMAND_TIMEOUT` | `120` | секунд на команду; `0` — без лимита |
| `CANDY_STOP_TIMEOUT` | `20` | секунд на каждый шаг остановки; `0` — без лимита |
| `CANDY_UI` | `menu` | `menu` (экран с меню) или `console` (строка `candy>`) |
| `CANDY_UPDATE_REPO` | `Vital-Candy/Candy-userbot` | репозиторий для `.update`, формат `владелец/имя` |
| `CANDY_UPDATE_BRANCH` | `main` | ветка для `.update` |
| `CANDY_LOG_DIR` | `logs` | каталог файловых логов; `off` — не писать в файл |
| `CANDY_LOG_MAX_BYTES` | `1000000` | размер файла лога до ротации |
| `CANDY_LOG_BACKUPS` | `3` | сколько старых файлов хранить |

API ID и API Hash в `.env` не хранятся: они вводятся при первом запуске и сохраняются в профиле аккаунта.

## Плагины

Плагин: файл `plugins/<имя>.py`, который экспортирует `create_plugin(app)`. Образец: `store/plugins/example.py` (ставится из магазина: `.store install example`).

```python
from core.plugin import Plugin

class MyPlugin(Plugin):
    name = "my_plugin"
    version = "1.0.0"
    min_core = "1.0"           # минимальная версия ядра
    requires = ("other",)      # другие плагины (имена файлов без .py), грузятся раньше

    async def setup(self):
        self.api.register_command("ping", self.ping)
        self.api.register_handler("new_message", self.on_message)
        await self.api.add_background_task("tick", self.tick, interval=60)
        await self.api.storage.set("key", {"любой": "JSON"})

def create_plugin(app):
    return MyPlugin(app)
```

`self.api` запоминает всё, что плагин зарегистрировал, и при выгрузке снимает это само, даже если `setup()` упал на середине или `teardown()` бросил исключение. Задачи видны в `.status` как `plugin.<плагин>.<имя>`.

- `register_command`, `register_handler`, `add_background_task`: как в диспетчере и менеджере задач, но с учётом и снятием.
- Чтобы команда попала в `.help`, задайте при регистрации `description` (одна строка: что делает), `usage` (например `.ping [текст]`) и `details` (подробная справка для `.help ping`: подкоманды, аргументы, примеры, права). В `details` не используйте символы Markdown (звёздочки, обратные кавычки, `__`): Telegram их отформатирует.
- `storage.get/set/delete/keys`: своё хранилище плагина (JSON, до 64 КиБ на значение, до 1000 ключей), отдельное для каждого аккаунта и плагина.
- `on_cleanup(callback)`: своё действие при выгрузке (закрыть файл, соединение).
- `logger`: журнал `candy.plugin.<имя>`.
- Конфликт имени команды с уже существующей, неподходящая версия ядра, отсутствующая зависимость или цикл: плагин не загружается, причина видна в `.plugin list`, остальные плагины работают.

Плагины выполняются в том же процессе и не изолированы. Ставьте только код, которому доверяете.

Управление из Telegram (только ADMIN, то есть владелец): `.plugin [list]`, `.plugin load|unload|reload|info <имя>`. `reload` перечитывает файл и заменяет команды и задачи без перезапуска userbot.

## Магазин плагинов (`.store`)

Плагины не входят в сам userbot: при установке и при `.update` их нет, папка `plugins/` после установки пуста. Они лежат в том же репозитории в `store/plugins/`, а список с версиями и контрольными суммами в `store/index.json`. В установленный userbot папка `store/` не попадает (ни через `installer.sh`, ни через `.update`), плагины скачиваются отдельно командой в Telegram и кладутся в `plugins/`, которую обновление ядра не трогает.

```text
.store                          список плагинов магазина и состояние каждого
.store info <имя>               версия, описание, зависимости, размер, SHA-256
.store install <имя>            показать, что будет установлено
.store install <имя> --yes      скачать, проверить и загрузить без перезапуска
.store update                   у каких поставленных плагинов есть новая версия
.store update <имя> --yes       обновить плагин
.store remove <имя>             выгрузить и удалить плагин, поставленный из магазина
--force                         заменить файл, который вы изменили сами
```

Защита (плагин выполняется с правами вашего аккаунта):
- файлы берутся только из репозитория обновлений (`CANDY_UPDATE_REPO`) по разрешённым адресам GitHub;
- файл ставится, только если его размер и SHA-256 совпали с индексом, имя и метаданные корректны, а код компилируется; иначе ничего не записывается;
- установка только по вашей команде и только после `--yes`; ничего не ставится и не обновляется само;
- файл с таким же именем, положенный не из магазина, не затирается; изменённый вами заменяется только с `--force`;
- если плагин не загрузился, прежнее состояние возвращается (при обновлении работает старая версия);
- состояние (что поставлено из магазина) хранится в `data/store.json`; удалять можно только поставленное магазином.

Чтобы добавить свой плагин в магазин: положите файл `store/plugins/<имя>.py` (класс, наследующий `Plugin`, с литеральными `name`, `version`, `description`, при необходимости `min_core` и `requires`; `name` совпадает с именем файла) и запустите `tools/publish.sh`: он сам пересоберёт `store/index.json` (или вручную `python3 tools/build_store_index.py`). Тест проверяет, что индекс в репозитории не устарел. Файлы из `plugins/` в публикацию не попадают никогда.

## Консоль

Локальная консоль запускается отдельно от Telegram event loop.

Команды:

```text
help
status [all]
plugins
plugin load <name>
plugin unload <name>
plugin reload <name>
plugin info <name>
account list | account use <id|@имя>
backup create | list | restore <файл>
stop
```

Ввод консоли не блокирует asyncio loop: `input()` читается в отдельном daemon-потоке, поэтому выход не ждёт Enter. Без терминала (фон, `nohup`, systemd) консоль не запускается.

## Жизненный цикл

Порядок запуска:

```text
Storage → Telegram → Events → Commands → Modules → Plugins → Console
```

Состояния (`core/lifecycle.py`): `new → starting → running → stopping → stopped`, при сбое запуска `failed`. Недопустимый переход запрещён, `stopped` окончательно.

Остановка и откат неудавшегося запуска идут одной последовательностью (`core/shutdown.py`): Console → Plugins → Modules → Background → Events → Telegram → Storage. Каждый шаг изолирован и ограничен `CANDY_STOP_TIMEOUT`: сбой или зависание одного (например, `disconnect()` в плохой сети) не мешает остальным, а база закрывается в любом случае.

Здоровье (`core/health.py`), команда `.status` (и `status` в консоли):

| Статус | Когда |
|---|---|
| ✅ ok | всё работает |
| ⚠️ degraded | упал необязательный модуль или плагин, либо фоновая задача сбоит |
| ❌ down | нет связи с Telegram, база закрыта, не запущен обязательный модуль или приложение не в `running` |

Отчёт строится из состояния модулей, задач и плагинов и сам не бросает исключений.

## Публикация на GitHub без личных данных

Скрипт `tools/publish.sh` создаёт новый репозиторий с одним коммитом, где автор — `Candy` с
адресом noreply GitHub. Перед отправкой он ищет в файлах секреты, адреса почты, номера телефонов,
`api_id`, личные и служебные файлы (базы, логи, ключи, сессии, `.env`) и запретные слова. Слова берутся
из `~/.candy-forbidden`, а ещё автоматически из имени и почты в `git config --global` и в профиле GitHub
(если там настоящее имя, оно тоже заблокирует публикацию).

Рабочая копия лежит в одной папке `~/.candy-publish`: перед каждым запуском она пересоздаётся, а после
успешной отправки удаляется (пробный запуск оставляет её, чтобы можно было посмотреть). Новых папок не
накапливается; остатки прежних запусков (`~/candy-publish-ГГГГММДД-ЧЧММСС`) скрипт убирает сам, если они
созданы им (автор `Candy`). Чтобы сохранить копию, задайте `PUBLISH_KEEP_WORK=1`.

1. Создайте файл `~/.candy-forbidden`: по слову или регулярному выражению в строке (настоящее
   имя, фамилия, город; кириллицу и латиницу пишите отдельными строками). Файл лежит вне проекта и
   нигде не публикуется:
   `printf '%s\n' 'слово1' 'слово2' > ~/.candy-forbidden`
2. Войдите в GitHub: `gh auth login`.
3. Пробный запуск (ничего не отправляет): `bash tools/publish.sh --dry-run`.
4. Настоящий запуск: `bash tools/publish.sh`.
5. Если репозиторий уже существует, скрипт остановится. Старая история хранит прежних авторов,
   поэтому удалите репозиторий на сайте (Settings, Danger Zone, Delete this repository) и запустите
   скрипт снова.
6. На GitHub включите в Settings, Emails: «Keep my email addresses private» и «Block command line
   pushes that expose my email». В Settings, Public profile поле Name не должно содержать настоящее имя.

### Выпуск обновления

Когда репозиторий уже опубликован, новые версии выпускаются так (история не переписывается, сверху
добавляется один коммит от `Candy`):

1. Поднимите `CORE_VERSION` в `core/version.py` (например, `1.2.0` на `1.2.1`).
2. Пробный запуск: `bash tools/publish.sh --release --dry-run`.
3. Выпуск: `bash tools/publish.sh --release`.
4. На устройствах с userbot выполните `.update`.

Публикация ничего не устанавливает сама: скрипт только отправляет код на GitHub, работающий userbot
не меняется, пока вы не выполните `.update`. Чтобы случайно не затронуть рабочую копию, распаковывайте
новый выпуск в отдельную папку (например `~/candy-release`) и запускайте скрипт оттуда. Из рабочей установки (где есть сессия Telegram) скрипт сам откажется работать.

Скрипт скачивает опубликованный репозиторий, заменяет файлы текущими, проверяет их на секреты и
личные данные, требует версию выше опубликованной и пушит коммит с тегом `v<версия>`.

Включите на GitHub двухфакторную защиту: команда `.update` выполняет код из репозитория, и тот,
кто получит доступ к аккаунту, получит доступ к вашим userbot.
